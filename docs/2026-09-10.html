Testing application resilience with Amazon SQS and AWS Fault Injection Service

This article explains how to use AWS Fault Injection Service to test whether applications gracefully handle SQS access failures by progressively blocking queue access across four escalating phases and measuring producer/consumer behavior through CloudWatch metrics. The methodology requires defining a clear hypothesis about expected failure handling (such as circuit breaker activation or local buffering) before the test, then comparing actual results to identify gaps in resilience mechanisms. Best practices include implementing exponential backoff for retries, circuit breakers, dead-letter queues, and setting stop conditions based on customer-impact metrics rather than queue metrics themselves.

AWS Architecture Blog · 4:05 PM

Validating multi-Region DR for Terraform Enterprise with AWS FIS

Athenahealth implemented a multi-Region disaster recovery architecture for Terraform Enterprise across us-east-1 and us-west-2 after an AWS regional outage blocked their engineering deployments, achieving a 12-14 minute Recovery Time Objective and sub-1-minute Recovery Point Objective using Aurora Global Databases and S3 cross-Region replication. Using AWS Fault Injection Service, the team validated the architecture across three phases—EC2/Auto Scaling failures, database failover, and S3 connectivity disruption—uncovering critical issues including configuration drift in DR launch templates and state file dependencies that would prevent failover automation when S3 became unreachable. The key lesson was removing all recovery dependencies on the impaired Region by hardcoding infrastructure identifiers in failover scripts rather than dynamically retrieving them from state files, supported by drift detection via CI/CD pipelines.

What algorithm did Windows XP use to choose your initial user picture?

Windows XP randomly selected your initial profile picture from a default directory using the RtlRandomEx random number generator seeded with GetTickCount(). It employed a one-pass reservoir sampling algorithm that sequentially evaluated each file, selecting it with probability 1/n (where n is the current count), ensuring each file had an equal chance of selection. This approach was more efficient than traditional two-pass methods and avoided complications if files were added or removed during execution, with a safety cap at 100 pictures sampled.
