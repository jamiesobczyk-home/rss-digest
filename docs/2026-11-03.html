Anthropic Research · 6:00 PM

Progress on provable inference for large language models

Anthropic has developed FlashProve, a system using cryptographic proofs (zkSNARKs) to verify that AI model responses genuinely come from a specific claimed model, preventing undetected model substitution or tampering. The system achieves proof generation at ~110 tokens/second for a 400B-parameter model on H100 GPUs, creating ~19MB proofs per 1,024-token request. Anthropic is releasing the code, technical report, protocol description, and formal Lean proofs under Apache 2.0, enabling independent auditing and potential applications in compliance verification and consumer security.

Foundry in the real world: Turning LLM hunches into verified findings – Security Loop Series, Part 2

Foundry is a security verification system that converts LLM findings into trusted evidence by using a four-role pipeline (Indexer, Detector, Triager, Reporter) with strict verification gates that validate every citation against actual code bytes. Rather than making models smarter, it creates a governance layer that enables LLM security tools to operate reliably in production by solving the trust problem—findings are only marked as true-positive if their file paths, line numbers, and quoted text verifiably exist in the target code. AWS Architecture Blog · 11:26 AM

How to run a DR readiness engagement

This article outlines a five-step framework for running a disaster recovery (DR) readiness engagement: establish scope through cross-functional kickoff, surface dependencies and gaps via structured assessment, build progressive validation tests, document findings to inform architectural decisions, and establish quarterly reviews to prevent drift. The framework is demonstrated through an enterprise case study where an initial DR exercise failed, exceeding the 5-hour recovery target by over 2x due to missing shared services, unverified dependencies, and manual DNS failover processes. After implementing the framework over four months—updating boundary maps, automating failover with AWS Application Recovery Controller, and pre-provisioning recovery environments—the subsequent exercise succeeded, validating the structured approach.

AWS Architecture Blog · 11:26 AM

Validating your DR commitment: From controlled test to real-world readiness

DR validation requires four progressive testing levels—tabletop exercises, planned failovers, surprise drills, and fault injection—each surfacing different gaps in ownership, configuration, coordination, and dependencies. Findings from each test feed back into the recovery decisions to iteratively strengthen the commitment, making the value of progressive testing not passing a single exercise but building a practice that improves every cycle.

AWS Architecture Blog · 11:26 AM

Three business decisions that define your DR success

Effective disaster recovery depends on three critical business decisions: defining recovery boundaries around complete business functions rather than individual applications, anchoring RTO/RPO targets to business consequences (not engineering assumptions), and accounting for the full dependency chain. Teams frequently miss recovery targets when shared services like authentication platforms are excluded from the recovery scope or when slower dependencies owned by other teams become the bottleneck.

AWS Architecture Blog · 11:21 AM

Automating the full AWS DRS agent lifecycle: Install, heal, and offboard

AWS provides an automated solution for managing Elastic Disaster Recovery agent lifecycle across EC2 instances using three SSM Automation documents controlled by a single EC2 tag value (yes/no/pause). The onboarding document installs and repairs agents every 30 minutes, the healing document responds to stalled replication events, and the offboarding document cleanly removes agents while tracking billing status. The solution addresses problems like stalled agents missing recovery point objectives and descoped servers continuing to generate replication costs.
